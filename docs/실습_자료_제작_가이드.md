# 컴퓨팅 핵심 실습 자료 제작 가이드

## 목적과 기준 자료

`"@@ 이론 개념을 다루는 n주차 실습 자료를 만들어줘"`라는 요청을 받으면 해당 주차의 `ipynb` 실습 자료를 제작한다. 이번 학기 강의계획서를 가장 먼저 확인하고, 해당 개념의 이론 교안을 검토해 오전 수업과 범위를 맞춘다. 지난 학기 자료는 설명 방식과 난이도를 참고하는 용도로만 사용한다. 사용자가 이미 완성하거나 승인한 내용은 임의로 바꾸지 않는다.

후속 수정에서는 사용자가 직접 편집한 현재 노트북을 먼저 읽고 이를 기준으로 작업한다. 이전 생성본이나 웹페이지의 내용으로 덮어쓰지 않는다. 사용자가 바꾼 작성 범위, 변수명, 빈 줄, 셀 순서와 삭제한 도입 문구를 보존한다. 변경할 내용과 확인 방법을 짧게 정리한 뒤 요청한 범위를 수정한다.

## 파일 위치

아래 저장 경로는 저장소 루트를 기준으로 한다.

- 실습 노트북: `practice/{n}주차 실습.ipynb`
- 문제 그림: `images/week{n}/week{n}_chal{k}.png` 또는 `images/week{n}/week{n}_extra{k}.png`
- 이번 학기 강의계획서: [2026-2학기 컴퓨팅핵심 강의계획서](<2026-2학기 컴퓨팅핵심 강의계획서.pdf>)
- 이전 학기 이론 참고 자료: `2026-1학기 이론 교안/` (로컬 전용, GitHub 업로드 제외)
- 조교용 웹 실습 안내: `website/week{n}_prac.html`

## 기본 구성

별도 요청이 없다면 도전문제 3개와 추가문제 1개로 구성한다. 학습 목표와 진행 순서는 필요한 경우에만 짧게 제시하고, 사용자가 삭제한 도입부는 다시 넣지 않는다. 각 문제는 다음 순서의 셀로 작성한다.

1. 문제 번호와 제목
2. 문제 상황을 보여 주는 그림
3. 문제 상황, 입출력 형식, 조건, 입출력 예시, 알고리즘 선택에 대한 생각해 보기
4. 학생용 스켈레톤 코드
5. 조교용 Solution 코드
6. 테스트 케이스 4개를 담은 Markdown 셀

기존 자료를 수정할 때는 승인된 문제 수와 셀 순서를 유지한다. 예를 들어 1주차는 도전문제 3개와 추가문제 1개, 6주차는 도전문제 4개와 추가문제 1개로 구성되어 있으므로 기본 구성에 맞추려고 문제를 줄이지 않는다. 기존 주차는 실제 노트북과 사용자의 최신 요청을 기준으로 한다.

## 문제 설계 원칙

도전문제는 이론 개념을 단계적으로 적용하도록 구성하되, 단순 문법 확인보다 실제 상황을 해결하는 맥락을 부여한다. 문제 사이에는 난이도와 사고 과정이 자연스럽게 이어지도록 한다. 추가문제는 조교의 별도 설명 없이 풀 수 있어야 하므로 도전문제에서 다루지 않은 자료구조, 알고리즘, 함수 또는 기능을 새로 요구하지 않는다. 이미 배운 요소를 다른 상황에 조합해 연습하도록 만든다.

## 알고리즘 선택에 대한 생각해 보기

도전문제와 추가문제 모두 문제 안내의 마지막, 입출력 예시 아래와 스켈레톤 코드 앞에 생각해 보기를 넣는다. 해당 상황에서 알고리즘을 사용하는 취지를 짧게 설명하고, 학생이 문제 조건과 알고리즘의 특성을 연결해 생각할 수 있는 질문을 2개 제시한다. 별도 제출 항목으로 만들지는 않는다.

- 제목은 `왜 이 정렬을 사용할까요?`, `왜 이 두 정렬을 비교할까요?`처럼 문제에 맞춘다. 다른 주차는 해당 자료구조나 알고리즘의 이름과 목적에 맞게 바꾼다.
- 단순히 알고리즘 이름이나 정의를 묻기보다, 문제의 요구사항을 만족시키는 이유와 선택의 장단점을 생각하게 한다.
- 정렬 문제라면 비교와 교환 방식, 동점자의 입력 순서, 이미 정렬된 정도, 교환 비용 등을 실제 문제 상황과 연결한다.
- 학습을 위해 지정한 알고리즘을 유일한 해결책이나 항상 가장 빠른 방법으로 설명하지 않는다. 학습 목적과 실제 성능상의 장점을 구분한다.
- 정답 코드나 구체적인 구현식을 그대로 알려 주는 힌트는 피한다. 추가문제의 질문도 이미 배운 범위 안에서 작성한다.

## 코드 작성 규칙

스켈레톤과 Solution의 전체 구조, 변수명, 입출력 형식은 서로 일치시킨다. 스켈레톤에는 학생이 작성할 핵심 부분만 안내 주석과 임시 코드로 남기며 정답을 직접 드러내는 힌트는 피한다. Solution은 실행 가능한 완성 코드로 작성한다. `None` 처리와 오류 출력은 함수의 반환 규칙과 문제 조건에 실제로 필요할 때만 포함한다.

### 학생용 스켈레톤

- 작성할 위치마다 `# To Do: [무엇을 해야 하는지 간략한 설명]` 형식의 주석을 둔다. 대괄호 부분은 실제 역할을 설명하는 한 문장으로 바꾸고, 내용이 없는 `# To Do:`는 남기지 않는다.
- 비어 있는 함수나 제어문 본문에는 `pass`를 사용한다. 임시 코드로 `return`을 넣지 않는다. `pass`의 첫 등장에서는 아무 동작도 하지 않는 임시 코드이며 구현한 코드로 교체한다는 점을 안내한다.
- 함수 전체를 작성하는 문제는 함수 선언, `To Do:` 주석, `pass` 형식을 기본으로 한다. 다른 작성 범위는 필요한 선언부, 입력, 반복문, 부모 클래스 등만 제공하되 사용자가 확정한 뼈대를 유지한다.
- 함수의 반환 규칙이 있다면 `To Do:`에도 그 역할을 간단히 적는다. 완성된 Solution에서 실제 값을 반환하는 `return`은 정상적인 코드이며 유지한다.
- `input()`에는 `첫 번째 회원 이름: `처럼 짧은 항목명을 안내 문구로 넣는다.

```python
def bubble_sort(weights):
    # To Do: 버블 정렬로 weights를 오름차순으로 정렬하세요.
    pass
```

### Solution의 설명 주석

- 셀 맨 위의 `### Solution ###` 표기를 유지한다.
- `# Sol:`은 학생이 `To Do:`와 `pass`를 채워 구현하는 부분에만 사용한다. 코드를 새로 추가했는지가 아니라 **학생의 작성 범위인지**를 기준으로 구분한다.
- 학생이 작성하는 주요 줄에 설명을 충분히 붙인다. 반복 범위, 비교 조건, 후보 갱신, 교환과 이동, 종료 조건, 반환값의 역할을 짧게 설명한다. 구역 전체에 한 줄만 붙여 중요한 동작의 설명을 생략하지 않는다.
- 이미 제공된 함수 선언, 입력과 자료 준비, 함수 호출, 출력, 완성된 보조 함수에는 `# Sol:`을 붙이지 않는다. 이 부분도 역할이 드러나도록 일반 `# 설명` 주석을 추가한다.
- 예를 들어 6주차 도전문제 4의 `bubble_count()` 본문은 `# Sol:`으로 설명하고, 제공되는 `selection_count()`와 입력, 복사, 호출, 출력 코드는 일반 주석으로 설명한다.
- 주석은 설명할 줄 바로 위에 같은 들여쓰기로 작성한다. 실제 동작과 이유를 설명하고, 반복마다 달라지는 값이나 횟수를 고정된 사실처럼 적지 않는다.

### 구조와 띄어쓰기 일치

- 현재 학생용 스켈레톤의 공통 코드를 Solution에도 그대로 유지한다. 변수명, 문자열, 연산자 주변 공백, 들여쓰기, 코드 구역 사이의 빈 줄을 임의로 바꾸지 않는다.
- `### Solution ###` 표기, 구현한 본문과 설명 주석을 제외하면 공통 코드와 빈 줄의 배치가 같아야 한다. 일반 설명 주석을 Solution에만 추가할 때도 기존 코드 줄과 빈 줄은 유지한다.
- 학생용의 `pass`를 완성 코드로 교체하되, 작성 범위를 넓히거나 이미 제공된 코드를 학생이 작성해야 하는 것처럼 바꾸지 않는다.
- 작성 범위나 입력 문구를 바꾸면 문제 안내, Solution 주석, 입출력 예시와 테스트 케이스에도 변경 사항을 반영한다.

## 그림 제작 원칙

각 문제마다 가로형 그림을 하나 제공하고 `images/week{n}/week{n}_chal{k}.png` 또는 `images/week{n}/week{n}_extra{k}.png`처럼 일관되게 저장한다. 새 주차를 제작할 때는 먼저 `images/week{n}/` 폴더를 만든다. 그림은 문제 상황과 입력 대상의 관계를 이해하도록 돕되, 계산식, 정답, 구체적인 풀이 순서를 노출하지 않는다. 노트북은 `practice/`에 있으므로 `<img src="../images/week{n}/week{n}_chal{k}.png" width="600">` 형식으로 삽입한다. 추가문제 그림도 같은 방식으로 `../images/week{n}/`를 참조한다.

새 그림에는 상황을 설명하는 짧은 `alt` 텍스트를 넣는다. 그림의 위치를 바꾸면 노트북의 상대 경로와 관련 검증 경로도 함께 갱신한다. 웹페이지에 포함된 그림은 원본 PNG와 별개이므로, 그림 내용이 바뀌었을 때는 웹페이지의 포함 이미지도 갱신한다.

## 테스트 케이스

문제마다 정확히 4개를 작성한다. 테스트 케이스 1은 문제에 사용한 예시 입력을 그대로 사용한다. 나머지는 일반 사례, 경계값, 빈 결과 또는 잘못된 입력처럼 서로 다른 동작을 확인하도록 고른다. 모든 출력은 Solution을 직접 실행해 검증한다. 문제 안내의 출력 예시에는 입력 프롬프트가 보일 수 있지만, 테스트 케이스 출력은 채점 기준에 맞춰 프롬프트를 제외할 수 있으며 이 차이를 임의로 통일하지 않는다.

문제 조건에서 허용한 입력 범위 안에서 사례를 고른다. 정렬에서는 중복값, 이미 정렬된 입력, 역순, 원소 하나와 허용되는 빈 리스트를 살펴본다. 동점 순서를 요구하는 문제는 실제 이름의 순서까지 확인하고, 성능 분석 문제는 무엇을 연산 한 번으로 세는지와 종료 조건을 명확히 정한다. 주석이나 띄어쓰기만 수정하더라도 기존 Solution의 동작과 공개 테스트 결과가 유지되는지 확인한다.

## 웹페이지와 자료 목록 반영

- 노트북의 문제, 스켈레톤, Solution과 테스트 케이스를 확정한 뒤 [웹사이트 제작 가이드](웹사이트_제작_가이드.md)에 따라 해당 주차의 웹페이지를 제작하거나 갱신한다.
- 노트북의 문제 조건이나 코드를 수정하면 이미 제작한 웹페이지의 설명, 코드, 예제와 실행 기록에도 반영한다. 웹페이지에서 별도로 삭제하도록 요청받은 소개 문구는 다시 가져오지 않는다.
- 생각해 보기, `To Do:` 안내, `pass`, 일반 주석과 `Sol:` 주석도 노트북과 웹페이지에서 일치시킨다. 코드 주석이나 빈 줄이 늘어나면 작성 단계와 실제 Python 실행 기록의 줄 번호도 다시 맞춰, 현재 강조 줄과 설명이 어긋나지 않게 한다.
- 웹페이지가 현재 스켈레톤에서 시작해 완성 코드로 전환되는지, 코드 복사에 주석과 줄바꿈이 포함되는지 확인한다. 새로운 한국어 설명을 추가하면 포함 글꼴이 해당 글자를 지원하는지도 확인한다.
- 새 자료가 완성되면 `website/main.html`의 해당 주차 실습 링크와 README 표를 갱신한다. 주제명은 목차와 일치시키고, 아직 없는 자료의 링크는 만들지 않는다. 상세한 목차 및 README 관리 기준은 웹사이트 제작 가이드를 따른다.

## Markdown과 최종 점검

실습 자료에서는 가운데점 기호를 사용하지 않는다. 입출력 예시와 테스트 케이스의 코드 블록은 언어 이름을 붙이지 않고 세 개의 백틱으로 시작한다. 완성 전에는 다음을 확인한다.

- 노트북 JSON과 모든 셀 ID가 유효하고 중복되지 않는가
- 스켈레톤과 Solution이 같은 요구사항을 구현하는가
- 모든 학생 작성 위치에 구체적인 `To Do:` 안내와 적절한 `pass`가 있는가
- `Sol:`은 학생 작성 부분에만 붙고, 제공 코드의 설명은 일반 주석으로 구분되는가
- 설명 주석과 구현 부분을 제외한 공통 코드의 띄어쓰기와 빈 줄이 일치하는가
- 각 문제 아래에 알고리즘 선택의 취지와 생각할 질문 2개가 있는가
- 모든 Solution과 테스트 케이스의 실제 출력이 일치하는가
- 이미지 경로가 유효하며 그림이 정상적으로 열리는가
- 추가문제가 도전문제에서 배운 범위를 벗어나지 않는가
- 사용자 지정 표현과 이미 승인된 수정 사항을 보존했는가
- 변경한 노트북과 웹페이지의 문제 내용, 코드, 테스트 케이스가 일치하는가
- 웹페이지의 코드 작성 단계와 실행 강조 줄이 최신 주석과 줄 번호에 맞는가
- 새로 완성한 자료가 목차와 README에 연결되어 있는가
